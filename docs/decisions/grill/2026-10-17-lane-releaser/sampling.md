## Risks
- [S1] [HIGH] Issue option (a) "labellers get admin" was never available on redrobot, and AC2's "if that person is not an admin" is the default case, not an exception: a repository owned by a personal account has exactly two permission levels, owner and collaborator, and on a private personal repo the owner can grant collaborators only `write`; so on every multi-engineer user-owned host `risk_tier.py`'s `permission == "admin"` test names exactly one human (the owner, who is also the lane's default fallback reviewer), and the doc step as drafted would present "only the owner can release, today" as a conditional the host might not meet rather than as the rule for that host class. — GitHub Docs, "Permission levels for a personal account repository" ("A repository owned by a personal account has two permission levels: the repository owner and collaborators"; "In a private repository, repository owners can only grant write access to collaborators"); `.github/scripts/risk_tier.py:290-296,316`; `docs/reference/lane-host-setup.md:54-56`; `.github/workflows/lane.yml:532` (`inputs.operator || github.repository_owner`)
- [S2] [MEDIUM] Q2's position ("admin is the wrong proxy; a write-level engineer green-lights a bot HIGH PR") reverses the rationale the 2026-10-16 grill recorded when it rejected S2/S6 ("the admin role is the key, whatever the admin count"; "it was never meant to require four eyes between humans") and its settled rule ("a write collaborator ... stays red until an admin human's APPROVED review on the head SHA exists"), yet AC1 records the outcome "with its reason" and lists no Revisits entry against that decision, so the decision log would carry two live answers to who releases HIGH. — `docs/decisions/2026-Q4.md:712-717,751-752`; `docs/decisions/grill/2026-10-16-risk-tier-scope/dispositions.md:8,12,16`
- [S3] [MEDIUM] AC2 adds the only step in the enablement order with no fail-closed signal and no owner for its dependency: every existing step surfaces its omission mechanically (a missing label makes `gh issue edit` error, a missing protected list makes every diff HIGH with the fix named in the check output), while "name who releases" is read by no code, and the step's precondition ("a per-host releaser set in `risk-tier` first, not yet built") is jarvis code the host cannot write and that no issue tracks once #2097 closes on the doc PR, so a host reaching that step has nothing to link and nothing that fails. — `docs/reference/lane-host-setup.md:84-104`; `.github/scripts/risk_tier.py:176-195`; `.github/actions/risk-tier/action.yml:8-11` (the action's only input is `bot-login`)

## Unmentioned alternatives
- [S4] Surface the limit at publish time instead of in a doc: `lane_publish.py` already resolves the labeller and posts the review request, and `risk_tier.py` already makes the `collaborators/{login}/permission` call; one such call on the labeller in publish, and when the answer is not `admin` a `::warning::` plus a second request to `LANE_REVIEWER` (the owner by default), is issue option (c) delivered with zero change to what releases the hold — missed because the four options were read as rules about release rather than about notification; trade-off: one extra API call under the bot PAT per HIGH PR, and an owner who receives review requests they did not ask for. — `.github/scripts/lane_publish.py:174-177,189-197`; `.github/scripts/risk_tier.py:290-292`; `.github/workflows/lane.yml:529-533`
- [S5] If a write-level release is ever built, make it a boolean action input (`release-on-write`) beside `bot-login`, not a per-host login set: on a personal-account host every collaborator carries the identical `write` role, so a login list cannot distinguish engineers there, and the stated position ("labeller is fine; one human suffices") already reduces to "any human write collaborator who is not the bot and not the author"; the existing exclusions (Bot type, `LANE_BOT_LOGIN`, head-SHA match) carry over untouched — missed because "configurable releaser set" was taken as the implied shape; trade-off: no per-engineer granularity (which that host class does not have anyway) and no operator literal in a shared-path config, which the AGENTS.md rule D16 cites would otherwise forbid. — GitHub Docs, "Permission levels for a personal account repository"; `.github/scripts/risk_tier.py:285-287,296`; `docs/decisions/2026-Q4.md:680-682`
- [S6] Have `risk-tier` report its own enforceability: `GET repos/{repo}/branches/{base}` returns a `protected` boolean readable with the job's existing `contents: read` token, so the check can append "advisory: base branch is not protected; this hold does not bind" to its summary — on a host where `protected` is false that line in the check output, not a doc step, is what a write-level merger would see before merging past red — missed because the proposal treats enforcement as given and only the releaser as the variable; trade-off: one API call, and a host that protects through rulesets rather than classic protection needs `GET repos/{repo}/rules/branches/{base}` as a second probe before the warning is suppressed. — GitHub REST "Get a branch" (`protected`, required boolean in the response schema); `.github/actions/risk-tier/action.yml:40-49`; `docs/reference/lane-host-setup.md:188-199`

## Challenged assumption
- [S7] That the identity of the releaser is what stands between a HIGH lane PR and merge on a non-admin-labeller host. On the only such host in view, redrobot, nothing can hold at all: it is a private repository on a plan where protected branches are a private-repo feature of GitHub Pro and above (rulesets API 403 "Upgrade to GitHub Pro", `master` `protected: false`), so neither `risk-tier` nor any other check can be made required, a write collaborator merges past a red check, and the lane's own `gh pr merge --squash --auto` is rejected there (the setup doc already says Free-plan private repos have no auto-merge), so every publish job would end red. The enablement order therefore cannot be completed at step 3.3 ("Add `risk-tier` to the required status checks") before the proposed new step is ever reached, and a per-host releaser set built "at adoption" would be code for a hold that cannot bind on its target. The precondition none of the four issue options or the drafted AC names is enforceability (plan upgrade, public visibility, or transfer to an organization, which is also the GitHub-documented route to roles beyond owner/collaborator); the doc step as drafted asks the host the second question before the first. — GitHub Docs, "GitHub's plans" (GitHub Pro lists "Protected branches" under "Advanced tools and insights in private repositories"); GitHub Docs, "Permission levels for a personal account repository" ("consider transferring the repository to an organization"); `.github/workflows/lane.yml:594`; `docs/reference/lane-host-setup.md:97-108`; problem-statement facts from `gh` (2026-10-17): `protected: false`, rulesets 403
