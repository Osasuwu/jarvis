## Risks
- [S1] [HIGH] "Merges in redrobot stay with a human" has no mechanism behind it: with no branch protection, a plain `gh pr merge` (no `--admin`) and a direct `git push origin HEAD:<default>` both land, and nothing in the stack stops either. The only merge guard matches `gh pr merge.*--admin` on Bash|PowerShell (jarvis-private `hooks/hooks.json:9`); redrobot's own hooks cover secret scanning and protected files only (`.claude/settings.json:12-28`, `mcp__github__merge_pull_request` is listed for the secret scanner, not for any merge block); and the classifier "allows pushes to any branch of the repository you're working in, including the default branch, and pull request creation by default" (code.claude.com/docs/en/auto-mode-config.md, "Common boundaries"). #2006 (deny `--admin`) therefore closes a door redrobot does not have, while the open one (ordinary merge / default-branch push) is named as a human-only step with no enforcement.
- [S2] [HIGH] "Collaborator comments passed as data, not instructions" inverts at the classifier layer. In the classifier's own requests "the classifier sees user messages, tool calls other than read-only lookups ... Tool results are stripped" (code.claude.com/docs/en/permission-modes.md, "How the classifier evaluates actions"), and "explicit user intent overrides the remaining soft blocks" (auto-mode-config.md, precedence). Issue text the orchestrator pastes into a sub-session's start prompt is therefore the sub-session's *user message*: the one channel the classifier treats as the developer's intent, whatever label the orchestrator puts on it. The lane bound dispatch to the exact body the human saw and refused edited bodies (`.github/scripts/lane_intake.py:5-7`, `_body_changed` at 85-91, `_bot_edited` at 94-96); the orchestrator keeps the issue-author check but drops the body check, and on redrobot the owner or any collaborator can edit an issue body while the author field stays the developer's.
- [S3] [MEDIUM] Both revisit criteria lack a data source. "≥10 of the developer's own issues to merge by 2026-11-18" is to be compared against a lane that had a ledger with `merged-unedited` / `merged-edited` / `closed-unmerged` rows and smoke rows excluded from the count (`lane-close.yml:3-6`, `lane.yml:37-44` `ledger-issue`/`ledger-smoke-issue`); the orchestrator records nothing equivalent, and the developer's own PRs and the orchestrator's PRs share one author (`scripts/claim_issue.py:26-28` names this indistinguishability as accepted). "Cards that waited >12 h" has no log: the payload states cards expire after a week, so by the 2-week check the unanswered ones have vanished and the count is memory.

## Unmentioned alternatives
- [S4] Durable pre-classifier rules instead of in-context boundaries and a future #2006: `permissions.deny` / `permissions.ask` entries in `~/.claude/settings.json` (user scope, which the repo cannot edit) for `Bash(gh pr merge *)` and default-branch pushes, plus a PreToolUse hook for the `git -C` / `git -c` spellings the rules miss — this is the docs' own "human checkpoint" recipe (auto-mode-config.md, "Add a human checkpoint"), it "blocks before the classifier is consulted", survives compaction ("a boundary can be lost if context compaction removes the message", permission-modes.md "Boundaries"), and applies unchanged to subagents, whose frontmatter `permissionMode` is ignored (permission-modes.md, "subagent work", point 2). Trade-off: a few more cards, which the proposal's own fallback (phone approval) already budgets for.
- [S5] Fetch, don't paste: have each sub-session read its issue itself (`gh issue view`) and keep the orchestrator's start prompt to the issue number and the task framing. Issue text then enters as a tool result, which the classifier strips and treats as untrusted ("blocking anything that ... appears driven by hostile content Claude read", permission-modes.md "Eliminate prompts with auto mode"), instead of as the user message. Record the body hash at dispatch and re-check it before the PR (port of `_body_changed`, `lane_intake.py:85-91`) to keep the lane's "the body the human saw" property. Trade-off: one extra tool call per sub-session; a trivial port.
- [S6] Scoped identity for sub-sessions rather than the developer's full token: a fine-grained PAT limited to the target repository with Contents/Issues/Pull requests write and nothing else, injected as `GH_TOKEN` through the Bitwarden wrapper the sub-sessions already receive env from (`hooks/bws-guard.py:3-4`). `gh` honours `GH_TOKEN` over the stored login (cli.github.com/manual/gh_help_environment). Keeps "agents act under my identity" at the author level while removing cross-repo reach (the developer's token covers SergazyNarynov/redrobot and every other repo the developer can write to) and bounding the accepted exfiltration risk to one repo. Trade-off: PAT rotation, one more secret.

## Challenged assumption
- [S7] "If work runs under the supervision of the classifier + orchestrator, the read-only boundary is not needed" treats two different things as one. The lane's boundary was (a) read-only scope and (b) identity separation: every lane commit and PR is authored by the bot (`lane.yml:21-23`), which is what makes agent work distinguishable from the developer's and what the `merged-unedited` ledger row measures (`lane-close.yml:4-5`). The proposal replaces (a) with the classifier, which its own docs scope as "reduces permission prompts but does not guarantee safety ... not as a replacement for review on sensitive operations" (permission-modes.md, Warning under "Eliminate prompts with auto mode"), and drops (b) without discussion. Yet the proposal's trust rule is authorship-based: "own issues" = issue author is the developer, "collaborator comments" = data. Once agents write issues, comments and PRs as the developer (`claim_issue.py:26-28` already concedes the one-login case cannot tell agent from human), an agent-authored issue is an "own issue" and the orchestrator dispatches it; an agent-authored comment is "mine", not data. The authorship signal the resolution relies on is the one the resolution erases. The orchestrator is not an action-level supervisor either: on event-driven turns it can only propose cards (payload), and its state is compactable, so "supervision" at runtime is the classifier alone.
