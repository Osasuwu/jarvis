## Risks
- S1 [HIGH] The §7 hold for HIGH/CRITICAL ("red until a human with write access approves", "same rule for AFK and interactive PRs") cannot be satisfied for interactive PRs. GitHub forbids authors approving their own PR, the only collaborator on both repos is `Osasuwu` (admin), and every recent interactive PR is authored by `Osasuwu` with 0 reviews. 20 of the last 40 merged jarvis PRs touch `.github/**`, `.claude/**` or `AGENTS.md`, so roughly half of interactive PRs could only merge by admin bypass. The merge policy forbids normalizing that bypass — `gh api repos/Osasuwu/{jarvis,like-current-song}/collaborators` → `Osasuwu admin` only; `gh pr list --state merged --limit 40` (authors and file paths); `.github/workflows/waiting-human-review.yml:3-6` already records "at one developer a review cannot be requested from oneself".
- S2 [HIGH] The computed tier is under-counting and partly controlled by the worker. (a) Run on a diff, `classify` can never return 3: class-3 needs an explicit `mechanical_criteria`, and no diff producer supplies one, so the "3→HIGH" mapping is dead. (b) `docs-only` short-circuits to 1, so `docs/reference/test-quality.md` (which AGENTS.md makes binding: "read first"), `docs/security/agent-boundaries.md` and the planned `afk-orchestration.md`/`threat-model.md` come out LOW and auto-merge. (c) The worker can edit `config/plan_review.yaml` and `agents/**`, which are not on the machinery list or the deny list, and a `pull_request`-triggered check runs the PR head's classifier and config, so the worker can lower its own tier — `agents/plan_classifier.py:86-102,125-131`; `agents/plan_classifier.py:79-83`; `config/plan_review.yaml:49-54`; `.github/workflows/agent-dispatch.yml:169` (deny list covers only workflows, hooks, settings, gitleaks, pre-commit and three scripts).
- S3 [HIGH] "Label edits only on its own issue/PR, enforced by the tool allowlist" is not enforceable, and the gap allows unattended self-propagation. `gh issue edit` takes several issue numbers. `Bash(...:*)` entries are literal prefix matches, which the workflow itself admits. The App's `issues:write` covers the whole repo. The worker's PR number is unknown when the allowlist is written. App-token label events do trigger workflows, so a misbehaving or injected worker can put `agent:dispatch` on another issue and start a new unattended run. §4 checks the issue author but not the label `sender` — `gh issue edit --help` (gh 2.87.3: `gh issue edit {<numbers> | <urls>}`, example `gh issue edit 23 34 --add-label`); `.github/workflows/agent-dispatch.yml:155-160`; the worker can likewise remove the required `waiting-human-review` label from its own PR (`.github/workflows/waiting-human-review.yml:48-53`).

## Unmentioned alternatives
- S4 Hold HIGH/CRITICAL AFK PRs by not queuing auto-merge for them, and/or have interactive sessions open PRs as the bot App as well. The first means the deterministic post-step (`agent-dispatch.yml:206-233`) runs `gh pr merge --auto` only for LOW/MEDIUM; the second makes the operator a non-author who can approve every PR. Either way the approval-identity problem in S1 goes away without a new required check that can never pass. Trade-off: the first hold is not server-enforced against someone manually enabling auto-merge; the second adds bot identity to the interactive lane.
- S5 GitHub-native CODEOWNERS on the machinery paths, with a ruleset requiring code-owner review, instead of a custom path list inside `risk-tier`. Code owners are read from the base branch's CODEOWNERS, so a PR cannot loosen its own path hold. That closes S2(c) without custom code, as the substrate rule prefers (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners). Trade-off: it still needs a non-author approver, so it pairs with S4's bot-authored PRs.
- S6 Per-repo lane workflows adapted from a jarvis reference, instead of one reusable workflow with thin callers. The repo already retired cross-repo canon sync because "every project needs a meaningfully different shape" (`docs/reference/github-repo-setup.md:10-17`). like-current-song confirms it: its tests are Flutter (`flutter analyze`/`flutter test` in its `ci.yml`), which the jarvis worker allowlist (ruff/pytest/compileall only, `agent-dispatch.yml:143`) cannot run. Its required review check is `verify-verdict`, not `code-gate`. Its label vocabulary uses `unsafe-for-afk` and has no `afk:*`. There is no `agents/plan_classifier` to compute `risk-tier`. Trade-off: copies drift; a reusable workflow at `@main` instead makes every jarvis change take effect in every host at once.

## Challenged assumption
- S7 The proposal assumes GitHub identity can tell "a human", "an interactive skill" and "an unattended run" apart. Intake relies on that for the author write-access check and "never applied by an unattended run" (§3/§4), and §7 relies on it for "a human with write access approves". In fact the only identities are the worker App and `Osasuwu`. `/to-tickets`, `/file-issue` and `/triage`, the operator himself, and any locally scheduled run using the same `gh` auth all act as `Osasuwu`. So "issue author has write access" passes for every agent-written ticket, "never by an unattended run" has nothing on GitHub to check against, and the human approval in §7 is either the PR author (forbidden, see S1) or not available at all. Every boundary that names a human therefore reduces to "not the worker App", and the design should be written as that weaker guarantee or get a real second identity.
