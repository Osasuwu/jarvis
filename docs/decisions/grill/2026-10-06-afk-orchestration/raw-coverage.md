### Assumptions

- **A1**: The tool allowlist and the App's permission set bound what the worker can affect (own issue/PR labels only, own branch, no comment reads).
  - If false: The worker, or an injection in issue content, can relabel other issues, push to other PR branches, forge the code-gate verdict comment, and run arbitrary code with the token under `pytest`.
  - Enforced by: Prefix-matching `--allowed-tools` only. Shell subprocesses under allowlisted commands are not bound (agent-dispatch.yml:143; #1976 comment on main).
  - Evidence basis: Proposal text ("enforced by the tool allowlist"). No test or mechanism scopes commands to an issue number or branch.
- **A2**: Required checks are trustworthy merge evidence once each is pinned to its expected `app_id`, with `code-gate` coming from "a different App".
  - If false: LOW/MEDIUM PRs auto-merge on a forged or worker-influenced pass.
  - Enforced by: Nothing for the inputs. `code-gate` selects its verdict from comments by any author (code-review.yml:444-447), every check runs on GitHub Actions app 15368, and pytest runs PR-head code.
  - Evidence basis: An asserted architecture contradicted by the current protection settings and workflow code.
- **A3**: There is a human approver distinct from the PR author and from the agents.
  - If false: HIGH/CRITICAL interactive PRs can't be approved (self-approval is forbidden), and AFK PR approvals can come from an agent running under the operator's token. The HIGH hold becomes either a routine admin bypass or an agent rubber-stamp.
  - Enforced by: Nothing. There's one collaborator (Osasuwu), agents run as Osasuwu with `Bash(gh pr:*)` allowed, and no `--admin` deny hook was found.
  - Evidence basis: The phrase "human with write access", taken from the general GitHub model, not this repo's single-account setup.
- **A4**: An issue with no `afk:*` label has been judged class 1.
  - If false: Unclassified issues — `/file-issue` output, Q4-"yes" issues, every like-current-song issue — enter the lane as AFK-eligible.
  - Enforced by: Nothing at intake. Absence of a label is treated as a positive verdict.
  - Evidence basis: The `/to-tickets` three-outcome table, which holds only for issues that went through `/to-tickets` §3a.
- **A5**: Host repos are configured like jarvis (auto-merge enabled, same check names, the labels present, the classifier code available).
  - If false: The reusable lane fails or degrades in like-current-song: no auto-merge, a missing `code-gate`/`gitleaks`, missing labels, and no `plan_classifier`.
  - Enforced by: Nothing. "Read from the API" reads the differences; it doesn't reconcile them.
  - Evidence basis: Extrapolation from jarvis. like-current-song's actual settings differ on every one of these points.

### Premortem — P1

**Failure narrative**: The HIGH hold can't be released legitimately. The only human is also the author of every interactive PR, and approval doesn't re-trigger `risk-tier` or clear the `waiting-human-review` label. Within weeks, HIGH PRs routinely go through admin merges or `gh pr review --approve` run by an agent under the operator's token. Meanwhile, PRs classified LOW (docs-exempt contract files, classifier config, a forged "No issues found." verdict comment) auto-merge without review. like-current-song never produces its ≥3 runs because auto-merge is disabled there and its backlog is device-bound or machinery, so the N-run gate stalls and the lane is rolled back as unauditable.

**Earliest preventive decision point**: §7's definition of the approving "human with write access". It needs to be settled against §2's identity model for a single-account operator whose agents act under that same account, before `risk-tier` and the HIGH hold are built on it.
