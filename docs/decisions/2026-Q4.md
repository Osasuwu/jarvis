### Worker identity — GitHub App installation token, not the operator PAT (#1966) — superseded 2026-10-07, see "AC-lock branch 1 → D1"

- **Answer:** every GitHub write by the AFK worker and its post-steps uses a GitHub App
  installation token. The App is not granted the Workflows permission, so a push touching
  `.github/workflows/**` is rejected server-side. The existing `APP_ID`/`APP_PRIVATE_KEY` repo
  secrets (unused since `merge-train.yml` was deleted in #1835) are reused if they belong to a
  suitable App. `AGENT_DISPATCH_PAT` is retired from the lane.
- **Why:** with the worker writing as the operator, every hold is advisory against it (it can
  remove its own label, approve-as-author is indistinguishable, label edits are logged as the
  operator); AP4/5/6/8/9 share this root cause (research C298); and it violates the standing rule
  against acting under the operator's own identity.
- **Alternatives:**
  - keep the PAT: rejected, five attack paths stay open and holds stay advisory.
  - machine-user account: rejected, the 2026-09-21 answer ("a separate account for the agent
    isn't possible") rules it out; an App is not an account.
  - `enforce_admins=true` (Rec 10): rejected as unnecessary for the worker — an installation
    token is non-admin, which is exactly the code-gate D19 condition.
- **Reversibility:** reversible (swap the token back); medium setup cost.
- **Confidence:** 0.8. Open refining items: pinning the expected source App on required checks
  (AP8), and whether the code-gate check-run App (code-gate D3) must differ from the worker App —
  if shared, the worker token must not carry `checks:write`.
- **Revisits:** 2026-09-21 "separate agent account isn't possible" — **held** (routed around, not
  contradicted); code-gate D19 (enforce_admins off, agents on a non-admin token) — **held**.

### Trust boundary — which issue text the lane obeys

- **Answer:** an issue is dispatchable only if its author has write access and its body is
  unchanged since `agent:dispatch` was applied; either check failing → the run refuses and
  comments. The worker reads the issue body only, never comments. `threat-model.md` names this
  boundary. Implementation of the body check (hash vs `updated_at`) is a later refining question.
- **Why:** on a public repo the action's write-access check covers the labeler, not the author
  (AP1); the body is read at run time, not label time (AP2). The threat model still says
  "prompt injection via issues: None (trusted input assumed)".
- **Alternatives:** rely on the operator's judgement at label time — rejected, AP2 defeats it
  after the issue was read.
- **Reversibility:** reversible.
- **Confidence:** 0.85.

### Lane distribution — reusable workflow in jarvis, thin caller per repo

- **Answer:** the lane is a reusable workflow in jarvis; each host repo has a thin caller that

### N-run gate — no new infrastructure until the lane passes 10 real runs

- **Answer:** N = 10 real runs across both host repos, ≥3 per repo; jarvis smoke runs count.
  *Real run:* dispatched on a backlog issue not created to test the lane. *Run passes:* ends in a
  checkable artifact — a PR (merged or held) or an escalation comment carrying the `run_id`; zero
  runs may end green with no artifact. *Gate passes:* ≥6 of 10 PRs merge without a human editing
  their code (a HIGH-held PR approved unchanged counts). An issue the App cannot serve (e.g. a
  workflow edit) is refused at intake, not counted. Counting starts once the App identity,
  merge-by-risk and the trust boundary are in the lane. Before the gate only three change kinds
  are admitted: fixes for a measured lane failure, controls for a named attack path (AP1–AP12),
  deletion. Barred: planner lane, research lane, auto-pickup, more host repos, new hosts, Agent SDK.
  #1809 (quota/cost) is the measurement over the window and a precondition for scaling past N,
  not for starting.
- **Why:** seven prior designs each built capability before volume (retrospective C71–C76); 10
  runs detect a failure mode with ≥25% incidence at ~94% probability and nothing rarer — stated,
  not hidden.
- **Alternatives:** N = 5 (too weak to see anything below ~45% incidence); N = 20 (with a thin
  backlog the gate stalls and invites synthetic issues); no rule (the repeating failure).
- **Reversibility:** reversible.
- **Confidence:** 0.6 on the value 10 and the ≥6 threshold (threshold chosen against design-8's
  3 merged of 7).

### Merge policy by risk (coupling point 1, final form)

- **Answer:** LOW/MEDIUM auto-merge on green required checks; HIGH/CRITICAL get
  `waiting-human-review` and never merge unattended. The tier is computed by a deterministic CI
  job from the diff (machinery paths — `.github/**`, `AGENTS.md`, `.claude/**`, gate scripts,
  test deletions, dependency manifests — plus diff size); the PR's declared line can raise the
  tier, never lower it (final = max(computed, declared)). One rule for AFK and interactive
  `/implement`, because it lives in CI. Replaces interim `/implement` AC2 (merge by repo state)
  for repos running the job; AC2a (`--admin` deny hook) stays.
- **Why:** self-declared risk is measured fail-open (129/257 PR bodies without a risk line, 59 of
  them self-merged); LLM reviewers catch 15–31% of human-flagged issues and are an injection
  target (AP10).
- **Alternatives:** self-declaration only — rejected, fail-open; LLM-reviewer tiering — rejected,
  weak recall + AP10; blanket human merge (jarvis-oss) — rejected, no volume ever passes it.
- **Reversibility:** reversible.
- **Confidence:** 0.75.

- **Answer:**

  - *Ledger:* one tracking issue. A bot post-step comments one row per run: `run_id`, lane SHA,

    job-level `if:`.

    statistical claim.
